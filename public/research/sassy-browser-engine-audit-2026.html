Sassy Browser engine audit: twelve page- and file-reachable defects, found and fixed

Sassy Consulting LLC · Shane Smith · Audit run 2026-06-10, fixes shipped in v0.11.0 (2026-06-20), published 2026-11-09

Summary. In June 2026 we audited Sassy Browser, our own browser with a from-scratch HTML/CSS layout engine and JavaScript interpreter written in Rust. The audit confirmed 240 findings across correctness, W3C conformance and efficiency. This write-up covers the twelve with a security impact: inputs that a web page or an opened file controls and that could crash the browser, exhaust memory, inject markup, or weaken how secrets and agent permissions are protected.

All twelve are fixed, each with a regression test, and the fixes shipped in v0.11.0. Anyone running v0.11.0 or later is not affected.

Scope and method

The target was the Sassy Browser source tree as of 2026-06-10. Sassy Browser is our own product, so this was first-party work; no third-party systems were tested.

  • Subsystem review. Nineteen AI-driven auditors each reviewed one subsystem (JS interpreter, parser and lexer, DOM, CSS cascade, layout, paint, networking and cookies, file viewers, authentication, the MCP agent interface and the Foreman policy engine), looking through four lenses: correctness, W3C conformance, efficiency and novelty.
  • Adversarial verification. Every high and critical finding was re-checked by a separate verifier that read the cited code and tried to disprove the finding. Findings that did not survive were dropped, and severities were corrected where the verifier disagreed.
  • Fix discipline. Each fix was re-verified against the current code first, then written test-first: a failing test that feeds the malicious or malformed input, then the fix, then the test passing.

Result: 240 confirmed findings (12 critical, 68 high, 113 medium, 47 low), of which 59 were W3C conformance gaps. Most of the critical items were correctness bugs, such as object equality and try/finally semantics, rather than security issues. They are not covered here.

1. Page-controlled crashes in the JavaScript interpreter

Five defects let one line of page script abort the renderer thread. "café".startsWith("c", 3) indexed a Rust string at a byte that is not a character boundary. arr.map(x => arr.push(x)) asked for a mutable borrow while an immutable one was still held. let a = {}; a.self = a; JSON.stringify(a) recursed without a visited set until the stack overflowed. Promise.any inserted rejection reasons at their input index into a vector that was shorter than that index.

The fifth was a memory-exhaustion bug: assigning a[1e9] = 1 grew a dense backing vector one element at a time to a billion entries, tens of gigabytes. A negative index also wrote silently to element zero.

Fix. String operations now slice on character boundaries. map and filter iterate over a snapshot, the same way forEach and reduce already did. JSON.stringify tracks visited objects and throws the spec TypeError on a cycle. Promise.any pre-sizes its error list. Dense array growth is capped at 16M elements and throws a catchable RangeError past that, as does new Array(n). (Commits 00a3638d, c20f24d3.)

2. Markup injection through the DOM serializers

The interpreter's innerHTML and outerHTML serializers emitted text and attribute values raw. A value containing <, >, & or ", set through textContent or setAttribute, came back out of innerHTML as live markup and could break out of the attribute or tag. That is an XSS-class bug for any page that round-trips user text through these properties.

Fix. Text nodes are escaped for & < > and attribute values for & < > " ', using the same helpers as the document serializer. <script> and <style> content is still emitted literally, as the HTML serialization spec requires. Six tests reproduce the injection and check that normal markup round-trips. (Commit 630d22ec.)

3. Untrusted-file denial of service in the document viewers

Sassy Browser opens local files as well as web pages, including medical imaging and office formats, so a crafted file is an attack surface. A 20-byte DICOM file declaring an element length of 0xFFFFFFFE forced a 4 GB allocation before the read failed. A JPEG-Lossless frame declaring 65535 × 65535 × 4 components requested about 68 GB. The DICOM tag browser byte-sliced string values and panicked on accented characters and emoji. The spreadsheet viewer's MIN and MAX called partial_cmp().unwrap(), so a single NaN cell, typed in or imported from an .xlsx, crashed the app.

Fix. Declared lengths are checked against the bytes actually remaining before anything is allocated. SOF3 dimensions go through a checked multiply with a cap. String values are truncated on a character boundary. MIN and MAX skip NaN. Each fix has a test that feeds the malformed input and asserts an error, not a panic or an oversized allocation. (Commit f83068e3.)

4. Device key protection and agent policy fail-open

The device master key signs the user's identity and derives the sync and data keys. At rest it was encrypted under a SHA-256 of the hostname, the home directory path and a fixed constant. Any local process could recompute all of those, so the encryption added no real protection.

Separately, Foreman is the policy engine that limits what MCP-connected AI agents may do inside the browser. It loaded its rules from config/foreman-policy.toml relative to the current working directory. When the browser was launched from anywhere other than the repository root, which covers every installed build, the file was not found and Foreman silently fell back to an empty rule set that allowed everything.

Fix. The wrapping key is now derived with Argon2id from a random per-install secret, kept in the OS keyring with a restrictive-permission file fallback. Foreman resolves its policy from the install location and fails closed, denying gated actions, when the policy is missing or unreadable. (Commit 899bac8d.)

Not covered here. The audit also found weaknesses in cookie handling: Set-Cookie Domain validation, host-only and path matching, and __Host-/__Secure- prefix enforcement. Those fixes are still in progress, and we will add them to this page once a release containing them ships.

Lessons

  • Byte offsets are not character offsets. Three of the twelve findings were one Rust mistake: slicing a str at an index computed in characters. We now ban raw slicing of page-supplied strings in the interpreter and viewers.
  • Never allocate a size the input declares. All three file-format DoS bugs trusted a length field. Check every declared size against the data actually present, or against a hard cap, before allocating.
  • Fail closed by default. A security policy that silently becomes allow-all when its file is missing gives no protection in exactly the deployments where nobody is watching.
  • Verify AI findings adversarially. Running a second, independent pass that tries to disprove each high-severity finding removed false positives and corrected severities before any engineering time was spent.
